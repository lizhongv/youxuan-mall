## 一、项目现状分析

### 1.1 项目定位

- **名称**：微同 / openwtai platform-wxshop（lipengjun92 维护，Apache 2.0）
- **类型**：前后端全开源的微信小程序商城
- **业务覆盖**：约 50 个业务实体、90 个 Controller，覆盖商品/订单/支付/营销/会员/微信公众号/后台运营。

### 1.2 模块结构

```
platform/
├── _sql/                  初始化 SQL（base.sql / mall.sql / sys_region.sql）
├── platform-common        公共模块（工具/异常/拦截/Redis/SMS/OSS/PDF）
├── platform-biz           业务层（service/dao/entity ~50 个实体）
├── platform-admin         后台管理服务（63 controllers + Quartz）
├── platform-api           小程序/H5 接口服务（27 controllers）
├── platform-admin-ui      Vue2 + ElementUI 后台
├── wx-mall                微信小程序原生
└── uni-mall               uniapp 商城（README 提及，仓库未含）
```

### 1.5 现有项目的优点

- ✅ **业务领域覆盖广**：商城核心域（商品/订单/支付/营销/用户/微信生态）相对完整。
- ✅ **微信生态实战完整**：mp / miniapp / pay / cp / open 五大模块都用到，是同类项目少见的亮点。
- ✅ **多 OSS / 多支付 / 多短信适配**：作为"对接第三方"的范本可参考。
- ✅ **后台脚手架成熟**：菜单+角色+组织+字典+定时任务+代码生成器是 renren-fast 流派的成熟实现。

### 1.6 现有项目的硬伤

- ❌ 技术栈整体落后业界 2-3 年（Vue2 / SpringBoot 2.7 / Webpack4 都已 EOL）
- ❌ 没有微服务、MQ、ES、Docker、CI/CD、链路追踪、测试
- ❌ 充斥 "Controller-Service-单表 Mapper" 贫血模型，无 DDD/状态机/领域服务概念
- ❌ Shiro 旧版多次 CVE，commons-httpclient 3.1 等远古依赖存在安全风险
- ❌ pom 显式 `skipTests=true`，几乎零单测
- ❌ 业务深度不足：库存简单、无售后、无秒杀、无搜索、无推荐

## 二、技术栈对照头脑风暴

按 **流量层 → 应用层 → 数据层 → 中间件 → 安全 → 高并发 → 可观测性 → 基础设施 → 前端 → 业务深度 → AI/大数据** 十一个维度全面比对。

打分含义：✅ 已具备 / ⚠️ 有但简陋 / ❌ 完全缺失

### 2.12 头脑风暴小结

> **当前项目 ≈ 一个 2018 年水平的单体 SSM 商城**。
> **大厂电商 ≈ 微服务 + 中间件矩阵 + 多级数据架构 + 全链路可观测 + 高并发场景化 + 大数据/AI**。
>
> **重叠度：业务领域 70% 覆盖；技术架构 < 15% 覆盖。**
>
> **结论：业务模型可以保留借鉴；技术架构基本要"另起炉灶式"重构**。

## 三、重构建议（取舍清单）

按 **"技术成熟度 / 学习价值 / 实施成本"** 三维度做取舍。

### 3.1 ✅ 必做（覆盖现代电商核心技术栈）

1. **Spring Boot 3 + JDK 17**（本机已是 17）—— 现代化基线
2. **Spring Cloud Alibaba 全家桶**（Nacos / Sentinel / Seata / OpenFeign）
3. **RocketMQ**（订单异步化、削峰、解耦标配）
4. **Redis 集群 + Redisson + 多级缓存 + Caffeine**
5. **Elasticsearch 8**（商品搜索 + IK 分词）
6. **ShardingSphere-JDBC**（订单分库分表）
7. **Spring Security 6 + JWT + OAuth2**
8. **可观测性三件套**：SkyWalking + Prometheus+Grafana + ELK
9. **Docker + K8s + Helm + GitHub Actions CI**
10. **高并发核心场景**：秒杀 / 库存 / 延迟关单 / 订单幂等
11. **前端**：Vue3 + TS + Vite + Element Plus，加微前端 qiankun
12. **完整测试体系**：JUnit5 + Mockito + Testcontainers + JMeter 压测

### 3.2 ⚠️ 选做（看时间余量）

- XXL-Job 替换 Quartz
- Canal 同步 binlog → ES（实时数据一致性）
- Apollo（Nacos Config 已能覆盖，重复度高）
- 营销中心补秒杀/拼团/砍价
- 售后中心
- Service Mesh / Istio（运维向，应用开发可暂缓）

### 3.3 ❌ 不做（性价比差或与重构主线脱节）

- 多活 / 异地容灾（需要真实流量训练，单机模拟价值低）
- 自研推荐算法 / 召回排序（属于算法领域，与后端重构主线偏远）
- 大数据 Flink/Spark 实时数仓（属于数据开发领域）
- 跨端 Flutter（属于移动开发领域）
- 自研 RPC / 自研 MQ（造轮子，不如吃透成熟方案）

### 3.4 🟡 关键决策建议

**强烈建议从零开新仓库（platform-cloud），保留原项目作为业务参考，不强行原地改造。**

原因：
- 原项目模块边界是按"admin / api"切的，与微服务"按业务域切"完全不兼容；强行重构会比新写更慢。
- 新仓库可以一开始就遵循 monorepo + 现代规范，不被旧坑拖后腿。
- 老项目可以留作 "Phase 0 业务对照参考"。

**备选方案**：基于已是微服务架构的开源项目（mall-swarm / pig）继续学，重构成本更低，但学习"从单体演进到微服务"的过程价值会缺失。

## 四、重构方法与步骤

总周期 **12-15 个月**（业余每周 ~20 小时）。每阶段都设交付物 + 简历可写点 + 验收标准。

| 父 pom 锁定版本矩阵（SB 3.3.5 / Cloud 2023.0.3 / Alibaba 2023.0.3.2 / JDK 17）+ 阿里云镜像 | `pom.xml` BOM | ✅ |

| 风险 | 应对 |
|---|---|

## 附录 D · 踩坑记录

### D.1 Phase 0（2026-05-09）

| 坑 | 现象 | 解决 |
|---|---|---|
| 不能 system-wide 装 Maven（auto mode 限制 + 无 admin 习惯） | `mvn` 不在 PATH | 改用 **Maven Wrapper**（`mvnw` / `mvnw.cmd` + `.mvn/wrapper/maven-wrapper.properties`），首次运行自下载到 `~/.m2/wrapper/dists/`，无需修改系统 |
| Maven 中央仓库 TLS 失败（"基础连接已经关闭"）| 直连 `repo.maven.apache.org` 超时 | 全部切到 **阿里云镜像** `https://maven.aliyun.com/repository/central/...`：① 父 pom 的 `<repositories>` ② mvnw 下载 URL ③ wrapper.properties |
| `mvnw.cmd` 注释里有中文括号（`(only-script style)`）导致 cmd.exe 解析为代码块 | 第一次运行报 `'nly-script' is not recognized` | mvnw.cmd 注释改为纯英文、不含未配对的括号 |
| 系统环境变量 HTTP_PROXY/HTTPS_PROXY 被 .NET WebRequest 继承导致下载受阻 | PowerShell `Invoke-WebRequest` TLS 错误 | mvnw.cmd 内 PowerShell 子进程显式 `[System.Net.WebRequest]::DefaultWebProxy=$null; $env:HTTP_PROXY=''; $env:HTTPS_PROXY=''` |
| 不继承 `spring-boot-starter-parent` 时 `repackage` goal 不会自动绑定 | 第一次 `package` 出来的 jar 只有 8KB，提示"中没有主清单属性" | bootstrap-app/pom.xml 显式给 `spring-boot-maven-plugin` 加 `<executions><execution><goals><goal>repackage</goal>` 配 `<mainClass>` |
| `/actuator/health` 默认 `show-details: when-authorized` 看不到组件细节 | 匿名访问只返回 `{"status":"UP/DOWN"}` 没有 redis/mysql 子项 | 启动时加 `-Dmanagement.endpoint.health.show-details=always`（dev only），或在 application-dev.yml 中改配置 |
| WSL2 Redis 默认 `bind 127.0.0.1`，按文档说法 Windows 侧 localhost 应该不通 | 实际测试 Windows 11 26100 上 `localhost:6379` 直连 OK，无需改 0.0.0.0 | Win 11 当前 WSL2 默认开启了 `localhostForwarding`（或 mirrored networking），保持 Redis 默认 bind 即可 |
| Spring Security 6 默认所有接口要鉴权，dev 阶段会挡住 `/api/ping` | 401 | `SecurityConfig` 显式 `.anyRequest().permitAll()` 全放行（Phase 1 末期再接 JWT 过滤器） |
